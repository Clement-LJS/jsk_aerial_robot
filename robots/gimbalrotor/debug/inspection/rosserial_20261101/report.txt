FINDING 1: BACKWARD IMU TIME STEP
Exactly one event, seen in both bags: delta -758,798 ns (-0.759 ms).
Previous IMU stamp: 1793511590.716732750.
Next IMU stamp:     1793511590.715973952.
The same backwards ordering is already present in valid USB input frames.
Thus this particular time step was not introduced by rosbag ordering alone.
The host time-sync response was submitted at 14:39:50.712986; the affected
IMU frame began arriving at 14:39:50.715871, about 2.885 ms later.
Clock synchronization/offset adjustment is the leading explanation for this
event. It is not proof of the exact MCU execution sequence, nor proof of the
separate shared-buffer corruption hypothesis. The local rosserial syncTime()
calls setNow(), replacing offsets without a monotonic-time guard.
The IMU estimator explicitly returns early for a non-increasing timestamp;
the angular-velocity output also carries this time step in the all-topics bag.

IMPLICATION FOR ROOT-CAUSE DEBUGGING
This is a useful clean-corruption baseline, not a deterministic reproduction.
Arming/control load plus this hand movement did not trigger the old corruption.
Prior disarmed corrupt packets mean arming is not a necessary condition either.
Continue using selected topics plus USB; record -a is not required for the known
corruption evidence. Begin both captures before commands and keep a disarmed
baseline; compare repeated stationary/moving/manual-control intervals without
increasing PWM just to provoke a fault. A future bad packet captured at USB can
separate host-side handling from corruption already present at USB reception.
The shared MCU serialization buffer remains a hypothesis supported by earlier
mixed payloads, not something confirmed or disproved by this error-free interval.
