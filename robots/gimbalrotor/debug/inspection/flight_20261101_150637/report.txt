MAIN CONCLUSION
The bags show a real, growing coupled roll/yaw/gimbal oscillation before LAND.
The strongest visible behavior is approximately 1.7 Hz in gimbal 4 target,
gimbal 4 feedback, roll gyro and yaw gyro. Commands themselves oscillate and
feedback follows with delay. This supports a closed-loop stability problem
involving attitude control, allocation and actuator dynamics. It does not prove
which gain, mechanical property, filter or latency is the original cause.

CONTROL PATH AND POSSIBLE CONTRIBUTORS
The selected controller is aerial_robot_control/gimbalrotor_controller and
navigation is gimbalrotor_roll_yaw_perching_navigation. Perching state remains
FREE_FLIGHT throughout; no perching engagement appears in the recording.
The local gimbal_calc_in_fc path sends allocation and translational force
components to the flight controller. FC attitude feedback terms then change
the force vector and atan2-derived gimbal angle; the FC applies a simple angle
low-pass update. Consequently rate feedback, servo response, filtering and
allocation coupling all matter to closed-loop phase/stability.
Source: robots/gimbalrotor/src/control/gimbalrotor_controller.cpp:254,288
Source: aerial_robot_nerve/spinal/mcu_project/lib/Jsk_Lib/flight_control/attitude/attitude_control.cpp:381,1208
Firmware equivalence with the checked local branch remains the earlier user
assumption; it has not been proven by matching a flashed image to a build.

Recorded gains: roll P/I/D 30/1.5/25; pitch 15/4/7; yaw 14/1/5.5.
The three rpy/gain messages have the same values, so no recorded gain jump
explains the onset. Strong growing D-term outputs accompany the oscillation.
That does NOT establish that increasing/decreasing a particular gain will fix it.
The recorded 8x3 inverse torque allocation matrix has condition number roughly

matrix. This is not a complete robustness analysis of the full allocator.
